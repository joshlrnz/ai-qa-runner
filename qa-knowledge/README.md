# QA knowledge base

Generated by the `build-qa-knowledge` skill. This directory is the map a planning agent reads
to turn free text ("check that a sales order can be created and approved") into a `TestPlan`
JSON document that `ai-qa-runner` executes.

Nothing here is a test. Nothing here changes application code.

```text
free text
  → planning agent (reads modules/*.md)
  → TestPlan JSON (validated by ai-qa-runner/src/contracts/test-plan.ts)
  → executeTestStep (resolves target names via application.json)
  → Playwright
```

## Writing a plan from this knowledge base

**The planning agent has no access to the application source.** Everything needed to compose a
valid `TestPlan` is in this directory, and anything not written down here does not exist as far
as a plan is concerned. Source paths in the module files are provenance for the humans
refreshing this knowledge base — not something the planner can open.

### The vocabulary is closed — six actions, nothing else

| action | fields | resolves against |
| --- | --- | --- |
| `navigate` | `path` | a value in `pages` |
| `click` | `target` | a key in `targets` |
| `fill` | `target`, `value` | a key in `targets` |
| `select` | `target`, `value` (option **label**) | a key in `targets` |
| `assertVisible` | `target` | a key in `targets` |
| `assertText` | `target`, `value` (substring) | a key in `targets` |

**Do not use `select` against this application.** Every v2 dropdown is a MUI `TextField select`,
which is a `div[role=combobox]` plus a popover listbox rather than a native `<select>`, and
Playwright's `selectOption()` throws on anything else. Pick from a dropdown in two steps
instead: `click` the combobox target, then `click` `shell.select-option` with `{optionLabel}`
bound to the visible option text.

If a scenario cannot be expressed in these six actions, say so and stop. Do not invent an
action, and do not substitute a different one that merely runs without error.

### Rules

1. **Every `target` must be a key that exists in `application.json`.** Never compose a selector
   inline; `resolveTarget` only looks up names.
2. **Every `navigate` path must be a value in `pages`**, with its `{placeholders}` bound.
3. **Never invent data.** Record ids, codes, names, option labels and credentials are
   parameters. A flow that needs one declares it; the caller binds it.
4. **Read the module's Preconditions before composing.** Most failures against this app are
   permission or tenant-edition problems, not selector problems: a Lite tenant is blocked from
   every `/v2/*` route during render, and `SHOW_PRICES` removes whole columns and panels.
5. **Prefer the flows already written** in `modules/*.md`. They are the verified shape. Compose
   a new one only when no flow covers the request, and follow the same step conventions.
6. **A target marked `low` confidence, or listed under a module's Open questions, is a
   hypothesis.** Using one is allowed; presenting the resulting plan as reliable is not.
7. **Destructive flows are marked with a blockquote.** Surface that to the caller before running
   one.

### Working with a specific record

Record ids are **supplied by the caller**, alongside `companyId`. An instruction like "open sales
order 8412 and change its invoice number" arrives with `{orderId}` already bound, so the plan
navigates straight to the record:

```
navigate → /companies/{companyId}/v2/sales-orders/{orderId}/update
```

There is no need to open a list and search for the record first when the id is bound. When an
instruction names a record only by its code (`SO-0123`) and no id is bound, use the module's
documented open-by-code flow where one exists (`v2-sales` "Open a sales order by code": search
the list, click the code link, guard on the update-only submit). Where a module has no such flow,
say so and ask for the id rather than inventing a row click — on several lists (products, for
one) the code cell is not a link and clicking the row does nothing.

Every record flow follows the same four beats:

1. `navigate` to the update path with the id bound.
2. `assertVisible` a control that proves the record loaded — see below.
3. `fill` / `click` the thing under test.
4. `assertText` against `shell.toast` for the outcome.

**Step 2 is not optional.** A wrong, deleted or inaccessible id still renders a page; without a
guard the plan fails several steps later with a confusing error. Pick a control that exists only
on a populated update page. Where the submit label differs between create and update — sales
orders use `"Save as Pending"` vs `"Save changes"` — the submit button itself is the guard. Where
it does not — purchase orders say `"Submit"` on both — guard on a record-only action such as
Cancel or Lock instead. Each module's flows show which to use.

Records in a state that forbids editing (locked, cancelled, completed) render the form read-only
with the submit removed, so step 2 fails. That is correct behaviour, but the error reads
"element not found" rather than naming the state — worth passing on to the caller when it happens.

### Things that are true everywhere in this app

- **Page titles are not headings.** v2 renders them through a custom typography variant with no
  element mapping, so they come out as `<span>`. `role=heading[…]` will not find a page title.
  Assert page identity with `assertText` against `shell.breadcrumb` instead.
- **Toasts are the success signal.** Mutations confirm through `shell.toast` (`role=alert`).
  There is no URL assertion in the vocabulary, so a create/update flow asserts the toast, not
  the destination.
- **Confirmation dialogs repeat the verb.** A destructive action opens a dialog whose confirm
  button is scoped as `role=dialog >> …`. Several confirms share a name with the page button
  that opened them — always use the module's `*-confirm-button` target, never the page trigger.
- **Form fields are addressed by id**, derived from the field's form path (`billing.customerId`,
  `payment.invoiceNumber`). This is deliberate: required fields append a `*` to their label,
  which corrupts accessible-name matching.
- **`role=` name matching is exact and case-sensitive** in the runner's Playwright. `[name="Save"]`
  will not match "Save changes". Substring matching needs `[name*="Save"]`, which a few targets
  already use where the accessible name is unstable.

| `routes.md` | every UI route in the app, parametrized, with its module and page file |
| `modules/<module>.md` | per-module targets, flows, preconditions, contract gaps, open questions |

| `.progress.json` | crawl state, so this is resumable across sessions |

| `scripts/validate.mjs` | checks every flow's targets and paths resolve, every `{param}` is declared, and reports action targets no flow invokes |
| `scripts/audit.mjs` | coverage report — which of the 234 pages are reachable by a flow, and the flow list per module |

## The app this maps

Next.js **14.2.35, Pages Router** — not App Router. A route is a file path under `src/pages`;
`[param]` is a dynamic segment and `index` collapses to its directory. There are no route
groups, no parallel slots and no per-segment `layout.tsx`. Shared chrome comes from HOCs in
`src/layouts/` (`authenticated`, `authenticatedV2`, `general`), which is why `shell` targets
live in `modules/shell.md` and are referenced by other modules rather than duplicated.

Selector strings must be valid for `page.locator()` in the runner's Playwright
(`ai-qa-runner` declares `@playwright/test@^1.63.0`) — see
`.claude/skills/build-qa-knowledge/references/selectors.MD` for the priority ladder.

The target repo's own `e2e/` suite belongs to a different runner and is **out of scope**:
nothing here reads it, reuses its selectors, or depends on its seed data.

## Parametrized paths

`pages` stores **path templates**, not literals:

```json
"v2-sales.sales-orders-update": "/companies/{companyId}/v2/sales-orders/{orderId}/update"
```

Every authenticated route in this app is tenant-scoped under `/companies/{companyId}/`, and
most record pages carry a second id. Storing literals would either pin the whole knowledge
base to one tenant's seeded data or leave 95% of the app unnavigable.

Each placeholder is declared in `params`:

```json
"companyId": {
  "description": "Tenant every authenticated route is scoped to. Constant for a whole run.",
  "source": "parameter",
  "scope": "run"
}
```

Every parameter is supplied by the caller at run time — there is no seeding, no fixture
mechanism and no environment lookup in this knowledge base. `scope` says how often a value
changes:

- `run` — bound once for the whole run. Only `companyId`.
- `flow` — bound per flow, by whoever composes the plan. The other 34 params, all record ids.

A flow that needs a record id declares it as an `<angle-bracket placeholder>` in its step
list and never invents a value.

### This needs a runner change

`ai-qa-runner` does not support templates yet. `assertKnownPath` is an exact-match check:

```ts
// ai-qa-runner/src/runner/execute-test-plan.ts
function assertKnownPath(path: string) {
  const knownPaths = new Set(Object.values(applicationKnowledge.pages))
  if (!knownPaths.has(path)) throw new Error(`Unknown application path: ${path}`)
}
```

It has to match the concrete path against the template set and substitute bound values
instead. Until that lands, `navigate` steps against this registry will fail. The change is
small and contained to `execute-test-plan.ts`, but it is a deliberate contract change and is
tracked in `index.md` under Known gaps rather than made silently here.

## Scope

In scope: **234** routes — `shell`, `v2-sales`, `v2-purchasing`, `v2-inventory`, `v2-finance`,
`v2-masterdata`, `v3-analytics`, `lite`.

Deliberately excluded at Checkpoint 1 (see `routes.md` for counts and reasons): `v1-deprecated`,
`v2-novellino`, `v2-reports`, and two dev-only pages.

## Refreshing this

The module markdown is the source of truth. `application.json`'s `targets` block is **generated**
from the target tables in `modules/*.md` — edit the markdown, then:

```bash
node qa-knowledge/scripts/compile.mjs    # rebuild application.json from the module files
node qa-knowledge/scripts/validate.mjs   # check flows, paths and params resolve
```

`compile.mjs` fails loudly on duplicate target keys and skips any target marked `unresolved`, so
an unresolved target never reaches the runner. `pages` and `params` are hand-maintained.

To extend coverage, re-run the skill: it reads `.progress.json` and `index.md` to find what is
done, so a refresh can target a single module without re-crawling the repo.

**Coverage is complete; correctness is only 1% verified.** A Phase 4 pass on 2026-09-17 confirmed
every route path and 4 of 405 selectors before the browser environment blocked it — see
`index.md` and `scripts/verify/README.md`. Every selector was derived by
reading source, so every target is capped at `medium` confidence. Phase 4 — resolving each
selector against the live app and checking the match count is exactly 1 — is what turns these
hypotheses into facts, and it has not been done. Expect a meaningful failure rate on first run,
concentrated in the targets already marked `low`.

### Coverage is audited, not assumed

Two numbers are checked on every refresh, and both are currently clean:

- **234 of 234 pages** are reachable by a flow (`scripts/audit.mjs`).
- **0 of 169 action targets** — buttons and submits — are uninvoked by any flow
  (`scripts/validate.mjs`).

Coverage comes in two layers. **117 named flows** are written by hand: the journeys worth
describing, with preconditions, guards and destructive warnings. Underneath, each module carries
a **route-flow table** giving the three-step shape (navigate → assert breadcrumb → assert guard)
for every page it owns. Read a row and emit it; that is the baseline proving each page renders
for the bound role.

Input targets that no flow fills are expected and fine — the registry is a vocabulary for
composing new flows, not only a record of the ones written. Action targets are different: an
uninvoked button means a user journey nobody can run, so `validate.mjs` fails loudly on those.

Where a control genuinely cannot be driven — file pickers, downloads, external services — each
module ends its flows with an **"Actions with no flow, and why"** table. The absence is a
recorded decision, not an oversight.
